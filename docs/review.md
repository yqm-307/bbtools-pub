# Review 职责

**何时读**：评审代码、设计或文档改动时。前置：[共用原则](principles.md)。职责是以证据判断正确性、风险和需求覆盖，不代替作者修改后再独立放行。

## 一轮评审要回答什么

1. **审的是哪一版、哪些要求？** 固定基线和候选，包含未跟踪的新文件；分别判断“有没有缺陷”和“是否做到了要求”。作者自述、空 diff、检查退出码都不是充分证据。
2. **责任是否闭合？** 按 P1 检查生命周期与失败责任，再看安全、并发和副作用；不先纠结排版或个人偏好。
3. **上层是否更容易用？** 按 P2 检查默认调用路径、概念数量及常规排障入口。只改名、搬入 detail 或减少公开方法数，不能单独证明封装改善；稳定重复是否值得按 P6 工程化处理？
4. **代价与诊断是否可信？** 按 P3–P5 核对公开承诺、错误后果和实际观测能力，不把“内部会处理”当作解释；测试是否能区分正确和具体错误实现？

## 按风险展开，不整套加载

| 改动或疑点 | 额外读取与检查 |
|---|---|
| 对象所有权、异步/并发、关闭、hook 或资源回收 | [生命周期与扩展评审](review-lifecycle.md) |
| API 或模块设计取舍 | [设计职责](design.md)，只读相关契约与取舍 |
| C++ 类型/公共头/构建兼容性 | [C++ 规则](coding-cpp.md)，只读相关章节 |
| 文档或注释 | [文档与注释](coding-documentation.md)，核实声称的事实；纯文档不默认读生命周期专项 |
| 新测试或覆盖有效性 | [用例设计](testcase.md)；确有并发再进入其专项 |

## 输出与边界

- 缺陷写清位置、触发条件、影响和证据；风格建议、未覆盖风险、尚无证据的疑问分开，不把建议包装成阻塞缺陷。
- 给出结论、已检查且无问题的范围、未能判断的范围及原因。完成/通过要绑定准确候选与实际检查；未跑、跳过、失败分别说明，不用 CI 全绿代替新路径验收。
- 必要复现用最小检查，不重跑作者整套测试，不为没有新证据的猜测不断加审。独立性或验证条件不足就如实说明。
- 不提交、推送、合并或修改权限；评审通过也不自动授予这些操作。指出可修的问题后交回作者，已经满足目标就停止。
