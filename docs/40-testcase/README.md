# 测试用例设计职责

**何时读**：为新行为、缺陷、回归或覆盖缺口选择和设计用例，或精简、删除已有用例时。先读共用原则，再进入本文件；只运行已确定的测试命令时不重新设计测试。发布放行归项目门禁，不由用例数量决定。

## 1. 从契约而不是实现选例子

找到行为来源，列出输入、结果、状态、资源责任和对外副作用。先覆盖生命周期和失败风险；未知要求标成待确认，不从现有实现倒推规格。

每个关键用例至少写清：

```text
前置条件 → 动作/事件 → 可观察结果 → 断言 → 能抓住的错误实现
```

正例：契约规定 `stock >= requested`，使用 `stock=4, requested=4`，断言成功，能抓住误写成 `>` 的实现。

反例：只用 `requested=5` 测不足库存；正确实现和错误的 `>` 实现都会失败，测试无法区分它们。

## 2. 选择最低但足够的验证层级

- 纯逻辑用单元测试；
- 公开边界用契约测试；
- 跨模块、真实线程/协程或外部依赖用集成测试；
- 只有低层级看不到风险时才上移，不用大测试替代明确的局部断言。

正例：容量拒绝策略在公开队列接口做契约测试，资源释放再用最小生命周期集成测试确认。

反例：为一个纯函数启动完整网络服务；或用 mock 调用次数通过来代替真实后端错误传播。

## 3. 先测边界和失败恢复

优先有效/无效输入、空值、最大容量、刚好边界、重复调用、取消、超时、异常、恢复和最终释放。涉及规则组合或状态变化时增加有意义的事件序列，不按“每个分支写一例”机械扩张。这份清单用来挑出与本次风险相关的情形，不是逐项补齐的任务。

正例：改一个同步、无状态的地址解析函数，只补空串、非法端口、端口刚好为 65535 和 65536 这几条输入边界。

反例：同一个函数也补上取消、超时、重入和关闭后调用的用例；这些情形在它的契约里根本不存在，用例只是在凑清单。

对每个用例代入一个具体错误实现：错误实现若仍能通过，调整输入、事件顺序或断言。覆盖率、通过数量和 mock 数量不能冒充区分力。

预期结果来自契约或独立参考，不用被测逻辑生成；同时确认夹具确实触发了目标条件，目标错误出现时对应断言会失败。

正例：用协议文档里的固定样例核对编码字节；关闭回归先确认确有在途回调，再触发 Close。

反例：编码和解码共用同一个错误，靠“编码后再解码等于原值”照样通过；或者只调用了 Close，就声称验证了关闭期间的回调交错。

## 4. 责任和副作用也要断言

不要只断言返回值。必要时断言：

- 额度、任务、连接或借用资源是否归还；
- 错误、未知结果和外部副作用是否可见；
- 重试是否造成重复执行；
- Close 后迟到结果、回调和新调用的行为；
- 观测是否改变对象寿命或顺序。

正例：超时测试同时验证底层是否仍可能执行，以及调用者能否区分未知结果。

反例：看到 timeout 返回就断言远端未执行；看到 Close 返回就断言资源已经物理释放。

## 5. 复用夹具但不伪造证据

控制时间、随机源和外部响应；mock 用于隔离边界。fake 能控制交错，但真实网络/外部系统的错误传播和资源行为仍需要对应集成证据。不要为了省时间把 fake 通过写成真实链路通过。

每条用例能单独运行，不依赖前一条留下的全局状态、端口或数据；夹具失败不能被当成业务通过，失败信息要指出是哪条行为不符合契约、实际值是什么。

正例：每条用例独立初始化并在结束时清理，失败时报告“取消后额度未归还：期望 0，实际 1”。

反例：依赖上一条用例建好的连接，失败时只报“整个流程超时”；或者后端服务没启动，用例直接返回成功。

## 6. 什么时候加、加什么样的

用例归属被验证契约的责任模块：下层语义在下层测，跨模块的组合由承担组合责任的模块测。

**该加的情况**：命中下表只是触发覆盖检查，先看已有用例能否复用或补强，不自动新增。

| 情况 | 加什么 |
|---|---|
| 新建模块 | 按契约写单元或契约用例，挑一两条能说明模块基本可用的打上 `smoke` |
| 新增或改变公开契约 | 在该模块公开接口上加契约用例，断言新行为 |
| 修复真实缺陷 | 能区分根因的最小回归，优先在已有用例或数据表里补一条；一条覆盖不了不同责任路径时才再加（命名见下文 badcase 规则） |
| 新增并发、取消、关闭或资源归还路径 | 能证明交错和收口的用例，见并发专项 |

**不该加的情况**

| 情况 | 原因 |
|---|---|
| 纯重构，且现有用例已覆盖受影响的契约 | 已有断言不改就该通过；需要改断言，说明它测的是结构。发现覆盖缺口时只补最小用例 |
| 下层模块已证明的语义 | 上层只测自己新增的组合和责任 |
| 能经公开接口低成本、确定地触发的内部行为 | 走公开接口测；不为测试扩大公共 API |
| 文档、注释、格式，以及不改变产物行为的构建调整 | 用链接、构建和格式检查；构建改动影响功能选择、依赖或测试注册时，验证对应产物 |
| 排障探针、一次性复现、诊断程序 | 结论留在仓外证据，确认的行为要求改写成回归用例 |
| 为覆盖率、通过数量或“每类情形都有一例” | 不增加区分力 |

变化探测用例指只固定契约没有承诺的内部结构或协作细节的用例：代码一重构就失败，行为错了却可能照样通过。契约要求的调用次数、顺序和副作用不在此列，例如回调最多触发一次、重试不重复写入，这些断言必须保留。

所有候选用例，包括命中“该加”表的，都过三个问题，三条都答得上才加：

- 有来源：对应一条契约行为或一个真实出现过的缺陷；
- 有增量：能抓住一个现有用例抓不住的具体错误实现；
- 层级对：放在能证明它的最低层级。

**加什么种类**：选能证明这条行为的最快种类。

| 种类 | 验证什么 | 要求 |
|---|---|---|
| `unit` / 契约 | 契约、边界和失败路径，是用例主体 | 快且确定，不依赖真实等待（见第 7 节） |
| `integration` / `live` | 真实线程、网络或外部服务 | 写明 fake 覆盖不到哪一段 |
| `perf`、泄露检查、疲劳测试 | 性能回归、资源泄露、长时间稳定性 | 写明它检出的风险 |

`smoke` 不是单独一类，而是从已有用例里挑出的少量、快速、确定、能说明模块基本可用的子集，与其他标签并存；不为冒烟另写重复用例。各类用例在开发中还是合入时运行，见[按阶段运行](execution.md)。

正例：新建 config 模块，按契约写版本切换和非法键的单元用例，再把“加载内存配置源 → 读取一个键 → Close”那条打上 `smoke`。

反例：新模块只有一条十分钟的疲劳测试；或者为了凑冒烟，把已有单元用例复制一份改名叫 `smoke_xxx`。

正例：修复关闭期间的回调重入，先确认已有关闭用例都在回调返回后才 Close，抓不住“在途回调访问已释放 owner”的实现，于是只补这一条交错用例。

反例：上层模块的测试重新建连接，逐项重测下层已经覆盖的半关闭、背压和超时语义；或者给每个公有方法补一条“调用后返回成功”的用例。

正例：队列重构前发现没有用例验证“取消后额度归还”，只补这一条；重构的其余部分不加用例。

反例：以“纯重构”为由，不补明显缺失的资源归还验证；或者重构后一批用例因为断言了私有成员而全部要改。

正例：验证请求分发，断言请求到达对应 handler 且响应内容正确；内部改成先排队再分发，用例不用改。另外断言取消后完成回调最多触发一次，因为这是契约。

反例：契约没有要求，却用 mock 断言分发器“先调 `Lookup` 再调 `Invoke`，各一次”；内部合并成一次调用，用例就失败，而把请求分错 handler 的实现照样通过。

正例：排查一次关闭卡死时写了带计时打印的探针程序，定位到“在途写入未等待完成”后删掉探针，把结论改写成一条行为用例 `close_waits_inflight_write`。

反例：把 `probe_close_hang`、`probe_close_hang_v2` 连同打印输出一起提交进测试目录并注册进测试集，断言只有“进程没崩”。

## 7. 时间是用例的成本

单元和契约测试不依赖真实超时或墙钟等待；逻辑到期优先用可推进的受控时钟或受控事件。必须验证真实计时链路或真实外部依赖的用例标为集成测试，并在用例说明里写明为什么不能更短。区分产品自身的超时和测试的兜底超时：前者是被测行为，后者只防止用例挂死，要留足余量。

正例：证明“worker 占满时新请求被拒绝”，用受控阻塞点占住 worker，断言拒绝后立即放行。

反例：连一个没有监听的地址，靠驱动十几秒的连接超时来占住 worker，再把它标成单元测试；整套单测的大半时间都花在这类等待上。

正例：验证“到期后返回超时”，推进受控时钟到期限，断言超时结果和资源归还；用例另设足够宽的兜底超时。

反例：把所有超时统一改成 50ms 就声称用例确定；或者为了“保险”设 5 秒，或在断言前 `sleep(100ms)` 等回调“应该已经到了”。机器一慢就偶发失败，机器一快就白白空等。

正例：真实 Redis 断线重连用例标为 `live`，说明里写明它要验证真实服务端关闭连接后的错误传播，fake 覆盖不到这一段。

反例：同样依赖真实服务和真实超时的用例挂着 `unit` 标签，被开发者当作秒级冒烟在每次改动后跑。

## 8. 精简和删除

已有用例同样按第 6 节检查。只有契约、故障模式和验证环境都已被另一条用例承接时，才删除重复用例，保留层级最低、区分力最强的一处；变化探测用例和已被契约用例完整承接的单次复现可以删除。长期跳过、空断言或说不清判错依据的用例先核查，不按运行历史直接删。删除时写明承接用例；说不清就保留并记录。

同一用例在多套构建或门禁里重复执行，要对应不同的故障检出能力，例如不同的构建模式、运行时版本，或开启内存、数据竞争检查工具的运行；产物、配置和验证目标都没有差别时才去重。门禁如何编排归项目规则。

正例：两条用例都只断言“满载返回拒绝”，保留同时检查额度归还的那条，删掉另一条，并在提交说明里写明承接关系。

反例：为了让测试数量好看，删掉唯一覆盖 Close 后迟到回调的用例；或者用 fake 的成功结果，替代唯一一条验证真实断线错误传播的集成用例。

正例：一条用例因为“环境暂不支持”被跳过了很久，核对后发现它的行为已经由新的契约用例覆盖，于是删除，并在提交说明里写明承接用例名。

反例：一条用例只剩一个恒真断言，说不出它能让哪种错误实现失败，却因为“删了覆盖率会掉”一直保留；或者反过来，删掉在内存检查工具下捕获释放后使用的唯一回归，只因为它的断言是“跑完没崩溃”。

正例：同一条生命周期回归分别在常规运行和开启内存或数据竞争检查的运行中执行，前者检查行为，后者检查内存或并发错误。

反例：同一产物、同一环境下无理由把同一批用例跑两遍；或者整套测试失败就整体重跑三次，把偶发失败重跑成全绿，也没人去查是哪条用例不稳定。

## badcase 进入测试契约，而不是历史正文

新 badcase 如果揭示了当前行为要求，就把它写成能区分错误实现的回归用例，并同步修正代码、当前文档和提示词中的概念。测试名、测试说明和断言都描述新行为；不要只新增一个带 issue 号的测试，把旧契约留在其他文件里。

正例：接口从“已完成”改为“已接纳但结果未知”，新增 `returns_outcome_unknown_after_deadline`，断言调用者能查询或补偿；文档和 Review 检查项都使用“未知结果”。

反例：新增 `regression_213`，只说明“修复了某次问题”，断言仍按旧的成功/失败二选一，后来维护者只能读提交历史才能知道真实契约。

## 按需展开

- 并发、回调、关闭、取消、容量或超时：读 [并发与生命周期用例](concurrency.md)。
- 决定开发中或合入时跑哪些测试：读 [按阶段运行](execution.md)。
- 需要确定业务契约而不是验证契约：进入设计职责；不能在测试中私自补规格。
- 测试文件命名、构建目标、注册和筛选命令：读对应语言的编码规则，C++ 见其“测试接入”部分。

## 证据和停止条件

交付关键用例及契约依据、风险、可区分的错误、实际执行结果或未验证原因；删除用例时交付承接关系。失败先区分产品、测试和环境；不放宽断言、跳过失败、整套重跑或加盲目等待来凑全绿。

当关键风险已有有效用例，或未知/未覆盖项已明确记录，且新增案例不再改变结论时就停。纯文档改动用链接、内容和脱敏检查，不硬造业务测试；未经授权不在共享或生产环境注入故障，也不为单个任务搭通用测试框架。
