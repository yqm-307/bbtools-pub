# 按阶段运行测试

**何时读**：决定开发中或合入时跑哪些测试。项目已有门禁脚本和命令时照用，这里只给选择依据。目标是开发中测试成本尽量低，合入时再放宽到全量和重型检查。

## 1. 用模块和标签选测试

每条用例属于一个模块，带一个或多个标签：`smoke`、`unit`、`integration`、`live`、`perf`；泄露检查和疲劳测试按项目约定单独标记或单独构建。`smoke` 是从已有用例里挑出的少量、快速、确定、能说明模块基本可用的子集，与其他标签并存，不另写一套。

模块边界与代码模块一致，“改了哪个模块”才能直接对应到“跑哪些测试”。测试名以模块为前缀、冒烟带统一标签，就能用测试工具的标签和名称过滤一步选出“某模块的冒烟”；具体命令写在对应语言规则或项目门禁里。

正例：HTTP 用例都在 `tests/http/`，测试名都是 `http.<行为>`；改 HTTP 解析时，一条过滤就能选出 HTTP 冒烟。

反例：一个 misc 测试文件里混着 HTTP、Redis 和 config 用例，只改 config 也得把 HTTP 用例一起跑；或者冒烟没有打 `smoke` 标签，只能靠记忆挑。

## 2. 开发中：只跑相关冒烟

每次改完要跑的：

- 改动模块的冒烟；
- 受影响下游模块的冒烟；
- 直接验证本次行为的最小用例集，包括这次没改过的已有回归，不以测试文件是否修改为界。

受影响下游指实际使用本次受影响接口、公共类型或行为的模块，不是所有依赖该库的模块。默认只看直接使用者；变化穿透了它的边界，才沿影响链继续往下游扩，到契约被隔离处停止。上游模块没有被改，不用为它跑测试。

这时不跑：无关模块、模块全量、`integration` / `live`、`perf`、泄露检查和疲劳测试；重型用例只按第 4 节的例外提前运行。

冒烟要少、要快、要确定。某个模块的冒烟慢到让人不想跑，先查等待、夹具和依赖成本，或换一条更轻的已有用例当冒烟。

正例：修复 HTTP 超时的错误映射，跑 HTTP 冒烟、使用该错误映射的 RPC 冒烟，再跑现有的错误映射回归，即使这次没改它，一分钟内得到结果。

反例：错误映射回归文件这次没改，于是只跑创建和关闭冒烟；或者改一行解析就本地跑全量测试加泄露检查，等二十分钟。

正例：HTTP 错误语义变化影响 RPC 响应，跑 RPC 冒烟；只改 HTTP 内部缓冲实现、对外行为不变时，不为所有依赖 HTTP 的模块跑冒烟。

反例：改了公共数据结构的字段含义，影响到 RPC 之外更远的调用者，却机械地只看一跳；或者反过来，凡是依赖这个库的模块一律跑一遍。

## 3. 合入时：放宽到全量

有行为改动时，合入门禁完成项目规定的全量用例（包括只带 `smoke` 标签的用例），以及适用的 `live`、性能回归和泄露检查，具体编排按项目门禁。纯文档等没有行为改动的变更，不因此强制业务测试。CI 已经覆盖的内容，本地不重复跑一遍来“确认”。

开发中省下的检查只是推迟，不是取消：被跳过或没有实际执行的检查不算通过证据；合入门禁失败，回到对应模块定位修复，不降低门禁、不整套重跑凑全绿。

正例：开发中只跑相关冒烟，提 PR 后由 CI 跑全量、性能回归和泄露检查；CI 指出 Redis 用例失败，就只在 Redis 模块复现并修复，再推一次。

反例：合入时也只跑冒烟就宣称通过；或者因为 CI 慢，把性能回归和泄露检查从合入门禁里挪走。

## 4. 例外：本次改动就是重型风险

只有本次改动确实改变了性能特征、内存所有权、泄露风险或并发收口语义时，才把对应的性能、泄露或交错检查提前到开发中，并且只跑相关的那几条。文件位于热路径上，不等于自动要跑基准。

正例：改缓冲区池的回收逻辑，开发中就跑该模块的泄露检查用例，不等合入时才发现泄露。

反例：改了调度热路径的算法，却说“性能留给 CI”，开发中一次基准都不跑；或者只是改了热路径上的一行日志文案，也把完整基准跑一遍。

做到改动模块和受影响下游的冒烟通过、直接验证本次行为的用例已执行、重型检查交给合入门禁或已按第 4 节跑过相关几条，就可以提交。
