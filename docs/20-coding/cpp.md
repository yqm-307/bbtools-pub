# C++ 编码规则

**何时读**：修改 C++ 实现、公开头、跨仓依赖、CMake 构建注册或 C++ 测试目标时。先读共用原则与 `20-coding/README.md`；本文件只补 C++ 约定，不回链上层，也不替项目真实构建配置作假设。

## 1. 语言、依赖与表达

- 以仓库真实构建配置的 C++17 为基线，不静默提升标准。标准库有成熟能力时先复用；不足时积极使用项目已选、成熟且适合的 Boost 组件，不因“不是 std”重复造轮子。新增依赖还要评估许可、安全、平台、维护、体积和退出路径。
- 类型、方法和函数沿仓库约定使用 `PascalCase`；成员用 `m_` 加 `camelCase`，非公开方法用 `_` 加 `PascalCase`；指针别名沿用 `Ptr`/`SPtr`/`UPtr`。存量风格与新代码冲突时，不借一次改动重命名全仓。
- 命名空间按模块组织，最多三层。模板服务于类型安全和稳定复用，避免技巧性、难诊断的元编程。
- 优先 RAII、值语义和适当的智能指针。`SPtr`/`UPtr` 分别对应共享和唯一持有；裸指针只有在非拥有关系或受控观察关系明确时使用。不能因为“异步可能还会用”就把所有对象改成共享持有。
- 错误用类型安全的结果、状态或异常表达，沿用模块已公开的返回码契约；只有确实保证不抛时才写 `noexcept`。工厂可以用 `Create` 和受限构造来约束创建路径。
- `volatile` 不提供线程间同步。跨线程状态按语义使用 `atomic` 或锁；多字段一致快照不能靠逐字段 atomic 自动保证。时间和时长优先用 `std::chrono`。

正例：一个请求对象被一个明确 owner 持有，异步任务只借用到完成事件；若必须共享，说明共享原因和最后释放责任。状态快照用同一同步协议保护，文档只承诺实现能证明的粒度。

反例：用 `volatile` 让多个线程读取状态，或把多个 atomic 的分别读取描述为“同一时刻”；用 `shared_ptr` 掩盖谁该结束任务的问题。

## 2. badcase 修正要迁移当前概念

如果实现修正了接口语义、错误状态、所有权或线程边界，沿调用者和文档入口搜索旧概念，再同步公共头、实现、测试、注释和提示词。不要把旧 API 说明留在注释里，再追加一个 issue 号解释“后来行为不同”。

正例：接口从“返回完成”改为“返回接纳结果，底层结果可能未知”，同步类型名、Doxygen、错误状态、测试断言和调用示例；历史原因留在 commit/ADR。

反例：头文件仍写“请求已完成”，实现可能返回 `OutcomeUnknown`，测试名却写 `regression_213`。编译通过不代表契约迁移完成。

## 3. 头文件与公共边界

- 公开类型有可定位的 `.hpp`；内聚小类型可以共处，不因类数机械拆文件。存在非内联实现时配 `.cc`，接口与命名空间、目录保持一致。
- 公开头不泄漏内部类型、第三方物理栈、异常类型或线程模型。无法隔离时明确兼容影响并在 Review 中核对。公共头的文档承诺必须和可观察实现一致。
- 头文件使用 `#pragma once`，include 按对应头、标准库、项目公共头、子模块头组织；避免依赖传递 include 让调用者“碰巧能编译”。
- 纯算法、类型工具和无状态小组件可 header-only；稳定 ABI、重状态、I/O 或编译成本需要时保留编译单元。不要为减少文件数把不同责任揉成一个头。

正例：公共 RPC 头只暴露协议契约和稳定错误类型，HTTP 具体类型留在实现或适配层；调用者无需知道内部传输栈。

反例：为了让一个测试方便，把内部连接类加入公共头；或在文档中承诺线程安全，但公共头和实现都没有说明同步范围。

## 3. 所有权、回调和资源

写代码时把 owner、借用者、回调注册者、注销者和最终释放者放在同一张责任图中。C++ 回调不能靠 timeout 强制中止；析构函数、持锁区域、准入和安全不变量保护区不能执行不可控外部逻辑。

正例：回调注册返回一个可等待注销的 token；注销后的在途调用有明确边界，回调捕获的对象不是临时引用。

反例：把一个成员函数绑定到局部对象地址，调用者销毁对象后仍由后台线程触发；异常从回调越过资源记账点，导致额度或连接没有归还。

## 4. 构建与格式

- `.clang-format` 是格式细则真源，`.editorconfig` 负责 UTF-8/LF 等文本约定。按项目格式检查改动行，不因功能改动顺手清洗全仓。
- 新模块、示例和测试必须接入真实 CMake 目标；不引入新 warning。固定已验收的跨仓版本，依赖或构建门禁失败时不能改用更底层命令绕过保护。
- CI workflow 只编排，执行逻辑放在仓库已有的 `scripts/ci/`；CI 修改和系统安装不属于普通 C++ 改动的默认权限。

正例：先使用目标工程的 CMake 配置和 pin，再运行聚焦 target/CTest；配置失败就记录为配置失败。

反例：CMake 因依赖 pin 拒绝后，手抄 build.ninja 的编译参数直接调用编译器，然后把它说成完整构建通过。

## 5. 测试接入

沿用项目已选测试框架；测试源通常位于 `tests/<module>/Test_<行为>.cc`，每个可独立构建为目标，CTest 名称按模块和行为注册。按实际性质标记 `smoke`、`unit`、`integration`、`live`、`perf`，不把标签当作证据本身。

检查构建开关、CTest 注册集和 CI 执行路径；空过滤、缺失二进制、`Not Run` 或被管道吞掉的失败都不能算通过。用例行为由 `40-testcase` 负责，本节只定义 C++ 文件、目标和注册约定。

**做到什么程度算够**：新代码遵守仓库真实编译约定，所有权与线程边界可解释，公共头没有无意泄漏，依赖门禁没有被绕过，测试目标真实注册且验证范围写清。
