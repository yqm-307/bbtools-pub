# 文档与注释规则

**何时读**：编写或评审注释、README、指南、设计说明、公共规范或脱敏文本时。先读共用原则与 `20-coding/README.md`；本文件只补文档职责，不要求回读其他层。纯文档 Review 也可以只从 Review 入口进入本文件。

## 1. 写当前契约和必要原因

- 中文为主，术语、API、类型和标识符保持原样；assert、异常和控制台诊断使用英文，业务 payload 不为了语言统一而翻译。
- C++ 公开类、函数、字段和文件职责按需用多行 `/** */` 块写 `@brief`，形态见 §7。默认构造、默认析构等没有调用约束的声明不机械加注释；带参数或有生命周期、线程、错误等约束的接口要写清这些事实。私有成员只有在名称不足以表达重要约束时才补说明。
- 不复述显然操作，不堆历史叙述；并发时序、所有权、容量和资源约束不能为了短而删除。线程安全、快照一致性、Close 语义和未知结果承诺必须匹配实现。
- 注释写“现在为什么这样做”，不要把 Issue/PR 编号、阶段代号、临时行号和会话过程写成长期契约。稳定 RFC/ADR 引用可以保留，但要确认文件真实存在。

正例：

```cpp
/**
 * 差：调用 Close 关闭对象。
 */

/**
 * 好：Close 后停止接收新请求；已接收请求按契约完成、取消或报告未知结果，调用者不需要操作内部回收链。
 */
```

反例：

```cpp
/**
 * 差：TODO 下一迁移窗口会解决这个问题（没有稳定来源）。
 */

/**
 * 差：这个 getter 返回同一时刻的完整快照（实现实际上分多个锁读取）。
 */
```

好例只是写法示意，落笔前仍需核实实际行为。文档不能用更肯定的句子替代码提供不存在的保证。

## 2. 新 badcase 直接修当前正文

文档、注释、README、指南、设计说明和提示词描述的是当前可用契约。出现新 badcase 时，先判断当前读者是否必须知道它：

- 必须知道：直接改唯一真源、相关代码/测试/提示词和正反例，删除过时表述。
- 不必知道：把诊断过程放在 commit、ADR、审查报告或私有证据，不把历史 patch 贴进公共正文。
- 必须保留历史：只保留影响当前兼容性、迁移、安全或不可逆选择的最小背景，并说明它对应哪个当前约束。

反例：`这个接口提供 a 功能，参数是 b、c；在 #213 中因为……所以……`。这把旧概念和新概念并排放在一起，读者不知道现在应该依赖哪一句。

正例：`这个接口提供 d（新的概念）功能；参数是 b、c；调用者按 d 的结果、错误和生命周期契约处理。` 历史原因留在变更记录，公共正文只保留当前事实。

改代码、规则文件或提示词时做同一检查：旧名称、旧错误语义、旧示例、旧路由和旧检查项是否仍会把读者带回 badcase。测试可以保留回归断言，但测试名称和说明也应描述当前行为。

## 3. 文档按层级各守一件事

```text
README.md                  定位、最短路由和阅读地图
00-principles/README.md    共同判断依据
10-design/README.md        契约、边界和取舍
20-coding/                 编码入口及 C++、文档专项
30-review/                 Review 入口及生命周期专项
40-testcase/               用例入口及并发专项
仓外/私有证据              日志、审查报告、阶段计划和会话记录
```

新路由只向下引用：根路由选原则和场景，场景入口只指向自己的专项，专项不反向要求读者回到上层。这样同一事实只有一个正文，不会把规范做成互相跳转的网。

旧平铺路径若必须保留，只放短兼容说明，不能复制正文。不要为了“每个目录都有 README”预建没有独立职责的文件。

## 3. 示例、指南和决策

- 可运行示例放 `examples/<name>/`，附目的、运行方式、依赖和期望输出；断言及验收放 `tests/`。依赖外部服务的示例不伪装成普通 CI 通过。
- 稳定架构与契约放架构文档；一个决策的收益、代价和放弃方案放对应决策记录。过程日志、运行输出、审查报告和临时计划留在仓外或私有证据中。
- 公开前核对文件、命令、API、链接、许可证表述和提交元数据。区分已实现、拟议、实测、未验证和历史事实。

正例：README 只告诉读者从根路由进入哪个场景，设计文档完整解释 Close 和失败后果，测试文档给出能区分错误实现的断言。

反例：README 复制一整套规范，coding、review 和 testcase 各再抄一遍；或者链接到仓库里不存在的 `LICENSE`、脚本或测试命令。

## 4. 公开脱敏

公开内容不能包含凭据、私有地址、绝对路径、原始日志、会话标识、内部主机名或不应暴露的产品内部标识。人工全文检查、定向模式检查和自动 secret scanner 是不同证据；未运行就不能声称自动扫描通过。

正例：文档描述“固定提交”并提供公开仓库路径，私有审查证据和本机路径留在仓外。

反例：把 `.omh` 路径、内部域名、运行时 delegation ID 或原始日志片段直接写进公共正文。

## 5. 实现文件里的注释

实现文件的注释写给维护者：大多数函数 1–2 句即可，只有复杂、核心的逻辑（状态机、锁与唤醒时序、跨线程所有权转交）才写成段；只写两类——**意图**（这一步为什么存在、要达成什么）和**操作说明**（读代码要花力气才能看出的做法）。不复述语法，不写历史。

**位置**：多阶段、持锁或有时序要求的函数，在函数体第一行放整体注释，写目的、阶段列表和约束；每个阶段前再放一个短注释块，编号对应整体注释。简单函数不需要整体注释。注释形态见 §7；公共契约只写在头文件声明处。

**含义**：先讲库内语义，再讲算法细节，并使用库内的原名（如 snapshot、admission、`out_notify`）：

- 生命期：对象由谁创建、持有到何时，借用或共享到什么时候结束。
- 所有权：现在谁持有，转交给谁，转交之后原持有者还能不能用。
- 控制权：谁有权修改这个状态，靠哪把锁、哪个相位或哪个返回码保证。

**"为了避免 X"必须带例子**：写出 X 是怎么发生的——哪条路径、哪个交错、造成什么后果。写不出这样的例子，说明理由没有想清楚，删掉这句话，不要用"避免死锁""保证安全"这类结论代替。

正例：

```cpp
void Scheduler::_AutoScaleTick()
{

    /**
     * 自动伸缩的一拍：把负载折成"该扩 / 该缩"信号，连续命中足够多拍才调整目标数。
     *   1. 门禁  2. 采样  3. 累计  4. 决策  5. 唤醒
     * 控制权：目标数只在 m_lifecycle_mutex 下改；手动入口持同一把锁，所以手动请求先到时，
     * 本拍持锁复查发现已是 Manual 就放弃。
     * 为什么要"连续命中"：避免抖动带来来回伸缩。例：队列水位一拍内冲高又回落，单拍触发会先扩出
     * 线程、下一拍又缩回去。
     */
    ...

    /**
     * 5. 唤醒：notify 的所有权从 _ApplyTargetLocked 交给本函数，必须退出全部锁后再发布。
     * 被唤醒的 worker 没有本地任务时会走 TryWorkSteal 取 map 锁，锁内唤醒只会让它一醒就撞上我们手里的锁。
     */
    _PublishNotify();
}
```

反例（括号里是读者的疑问）：

```cpp
/**
 * 差：这里先释放锁，避免死锁。（哪两把锁、哪两条路径？读者无法检验）
 */

/**
 * 差：这里加 1。（复述操作，没有意图）
 */

/**
 * 差：用 shared_ptr 保证安全。（谁的生命期、被谁借用，都没有说）
 */
```

写完逐条核对注释里的断言：锁序、线程归属、"不会为空"之类的话必须能在代码或锁序文档里找到依据；找不到就改成已知事实，不要用更肯定的措辞替代码承诺。

**做到什么程度算够**：读者能从文档知道当前契约、适用层级、真实入口和限制；示例不制造不存在的能力；注释没有把实现偶然性升级为公共承诺；复杂函数有体内整体注释，注释断言有依据；发布前路径、链接、空白和敏感内容均有对应检查。

## 6. 公开头 Doxygen 排版

- 有调用者需要知道的公开成员用 `/** */` 块：首行 `@brief 摘要`，续行与摘要对齐；空一行 ` *` 后依次写 `@param`、`@return`；无参数无返回值只写 `@brief`。默认构造、默认析构和没有特殊约束的空函数可以不写注释。带参数的构造函数按普通接口写清每个参数及其所有权、寿命或前置条件。成员声明之间空一行。
- 一族函数（同名重载或同一类能力）共用一个 `@name X 系` 分组块，用 `@{`/`@}` 包住；`@brief` 与正文写这一族共享的语义。
- 组内每个有文档价值的成员仍要被文档化：每个成员上方各放一个短 `/** */` 块，只写与同族不同的 `@param`/`@return`，成员之间按 §7 空一行。没有特殊语义的默认构造、析构和空函数不为凑齐警告而补空注释。示例见 `examples/FunctionFamily.hpp`，已用 doxygen 1.15、`WARN_IF_UNDOCUMENTED`、`WARN_NO_PARAMDOC` 验证零警告。

## 7. 注释形态

公共契约和需要展开的实现原因使用多行 `/** */` 块；短小、重要且只服务于私有成员的说明允许使用对齐的行尾 `//` 注释。不要为了覆盖每个声明机械添加注释：

- 多行块使用 `/** */`：`/**` 独占一行，正文每行以 ` * ` 开头，` */` 独占一行。不用 `///`、单行 `/** ... */`、行尾的 `///<` 或 `/* */`。私有成员的短说明可写在声明行尾，用 `//` 表达一个重要且简短的约束，并尽量对齐；复杂对象、生命周期、所有权和时序说明仍使用上方的多行块。
- 注释块写在它说明的代码上方，紧贴那段代码；整组（注释块加它说明的代码）和前后代码各空一行。函数体或 `{` 开头的第一个注释块，与 `{` 之间也空一行。
- 函数体和控制流语句的行尾注释移到所说明的代码上方。被注释的语句是无花括号 `if`/`else`/`for`/`while` 的执行体时，注释放到控制头上方，不插在控制头和语句之间；私有成员的短说明按上一条规则允许保留在声明行尾。
- 例外：文件第一行的 `@file` 块上方无代码，不空行；`private:` 等访问说明符后不能空行（`.clang-format` 设了 `EmptyLineAfterAccessModifier: Never`，格式门禁会删掉）；命名空间结尾只写 `}`，不写 `// namespace ...`。
- 实现文件里也用 `/**`：各仓 Doxygen 只扫描头文件、不提取私有成员，实现文件的注释不进文档。头文件函数体内（如模板实现头）的 `/**` 块会被 Doxygen 并入该函数的公开文档，消费仓 Doxyfile 需设 `HIDE_IN_BODY_DOCS = YES`。

```cpp
void StackPool::_ReleaseOneIdle()
{

    /**
     * 逐个在锁内摘空闲并更新计数，解锁后销毁再继续：
     * 不为回收额外分配收集 vector，避免清理路径再分配失败。
     */
    ItemType* item = _TakeIdleLocked();

    /**
     * 锁外 delete + Profiler 事件。
     */
    if (item != nullptr)
        _FreeItem(item);
}
```

反例：`_FreeItem(item); // 锁外销毁`、`size_t idle{0}; ///< 空闲数`、把默认构造和析构各写一段空泛 `@brief`、单行 `/** @brief 当前数量。 */`，以及注释块和上一段代码之间不空行。
