# 共用原则

本层适用于设计、编码、Review 和用例设计。它只回答“为什么这样判断、什么不能破坏”，不规定某个场景的命令顺序，也不指向其他层级。读者从根 `README.md` 进入本文件后，再回到根路由选择一个场景入口；本文件本身不回链，避免形成环。

## P1：先把责任闭合

生命期、所有权和责任是第一优先。开始设计或修改前要能回答：谁创建，谁持有或借用，谁在异步期间保证存活，谁处理失败、取消、关闭和最终释放，谁承担结果、资源和对外副作用。责任不只指内存，也包括任务、回调、队列额度、连接、结果和重试。

正例：一个对象把工作交给异步队列时，接口明确 owner 持有任务所需状态到完成或取消，队列满载时归还额度，回调注销后不再访问已经失效的对象。

反例：接口返回成功后把对象交给后台任务，却默认调用者会“活得够久”；关闭只改变一个标志，未说明在途任务、回调和资源什么时候结束。

判断问题：成功、异常、取消、重复关闭、构造半途失败和最后一个引用释放时，是否每一份责任都有唯一承担者？如果需要调用者猜内部回收顺序，责任通常没有闭合。

## P2：封装要降低理解成本

内部可以复杂，但对外的概念、步骤和排障入口应减少。在安全和责任已经闭合的前提下，简单、易用、可靠优先于更多特性和微观性能。用户不应为了完成默认动作而理解内部状态机、回收链或配置矩阵；高级诊断仍可以下钻，但不能成为日常使用前提。

正例：对外提供“停止接收新请求并等待现有请求结束”的服务语义，内部如何拆任务、归还连接和回收缓存由模块承担；出现失败时提供稳定的错误和状态入口。

反例：把内部 `ServerV2`、阶段编号和多个 manager 的组合直接暴露给调用者，声称“只是少了几行转发”；遇到问题只能阅读内部实现才能判断下一步。

判断问题：调用者需要记住的概念是否变少？常见故障能否依据公开契约和诊断入口处理？如果每个简单动作都要先读内部源码，说明复杂度泄漏到上层。

## P3：代价、结果和副作用不能隐瞒

没有完美决策，也没有没有代价的能力。设计要让使用者知道能力边界，发生问题时知道实际结果和影响。内部恢复且外部语义确实未变时，不必逐个暴露内部细节；但不能隐瞒重复执行、数据变化、延迟、费用、资源占用或未知结果，更不能把“无法确认”报成成功。

正例：请求超时但底层不能中止时返回“结果未知”，同时说明后续查询或去重方式；内部重试成功但增加了延迟，公开延迟承诺和重复副作用仍按实际情况处理。

反例：日志里记录了超时，接口却返回成功；内部自动降级丢弃了一部分数据，只告诉调用者“服务正常”。

判断问题：使用者会因此改变重试、补偿、对账或资源管理决策吗？会影响决策的事实必须能从结果、通知、状态或诊断入口看到。

## P4：扩展能力不能夺走控制权

灵活且可控的 hook 有价值；在必须严格控制的路径中禁止不可控的外部逻辑。只读通常风险较低，但仍可能阻塞、抛异常、重入、泄露数据或延长寿命。不能只凭“只读”“回调很快”“有 timeout”这些名称或约定声称安全。

正例：在主状态提交后发布不可变快照事件，明确执行线程、是否持锁、回调异常处理、注销后的在途调用和可见数据；严格准入路径不调用任意业务回调。

反例：在持锁、析构、额度分配或安全判断中调用可由外部替换的函数，再用文档要求“请不要阻塞”代替控制；把全局测试开关改名后当成正式扩展 API。

判断问题：谁能注册和注销？注销何时生效？回调能否重入、挂起或抛异常？外部逻辑影响了哪一个不变量？如果答案只能靠使用者自觉，控制权已经丢失。

## P5：可观测性必须可用

设计时就提供知道状态、失败原因和排查入口的实际方式。profiler、debug、trace 和统计可以按规模选配或默认关闭，但接入能力不能缺席；观测不应意外保活业务对象、破坏顺序、改变同步关系或泄露敏感数据，同时要说明开销、精度和开关影响。

正例：公共接口提供稳定的状态快照和失败原因，细粒度 trace 默认关闭但有明确启用方式；快照说明是否一致、采样时间和可能的并发限制。

反例：只在开发者本地加打印，没有公开排查入口；统计对象保存强引用导致业务对象无法回收；文档承诺“同一时刻快照”，实现却跨多个锁分段读取。

判断问题：常见故障能否先依靠公开信息定位？观测会不会改变对象寿命或时序？读者能否知道打开它要付出什么代价？不要求每个值类型单独造 profiler 模块，但必须有匹配系统规模的能力。

## P6：用工程化消除稳定重复

反复产出大量类同代码，是检查复用能力、数据表达、生成方式或边界设计的信号。先确认重复部分的共同语义，再选择复用、重构、生成或自动化；不逐处复制修补，也不因外形相似就搭通用框架。新增抽象、依赖或工具必须降低整体理解和维护成本。

正例：多个协议类型重复做相同的生命周期收口，先提取已证实的共同责任边界，并保留类型差异；重复的测试输入由数据表驱动，断言仍明确。

反例：每次遇到相似 bug 都复制一段修复；或者仅因两个类名字相似就建设一套万能基类、事件总线和配置系统，迫使所有使用者学习更多概念。

判断问题：重复的是语法还是责任？抽象后调用者是否更简单、错误是否更容易定位、边界是否更清楚？如果只是减少文件行数，却增加理解路径，工程化方向是错的。

## 统一判断顺序

先问责任是否闭合，再问默认路径是否简单，再问后果是否可知；之后检查扩展控制、观测入口和重复处理。任何后续性能或特性收益都不能掩盖前面的硬缺口。这个顺序是判断依据，不是要求每次任务填写同一张表。
