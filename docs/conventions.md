# 共用编码与维护规范

本规范提炼自多仓库的共同约定，覆盖 C++ 注释、代码风格、技术设计取舍与 Review 要点。各仓库在自身规范中引用本文件；与仓库现有约定冲突时，以该仓库的明确决策为准，不做无关格式迁移。`.clang-format` 是 C++ 格式细则的唯一真源，本文件不展开其参数。

---

## 1. 命名

- 类型（`class`、`struct`、`enum`）使用 `PascalCase`；方法和函数使用 `PascalCase`。
- 成员名使用 `m_` 前缀加 `camelCase`；`private`/`protected` 方法使用 `_` 前缀加 `PascalCase`。
- 类型别名使用 `Ptr`、`SPtr`、`UPtr` 等后缀；枚举值遵循所在模块既有风格，不借规范迁移改名。
- 命名空间按模块层级组织，最多三层；禁止新增四层及以上嵌套，过深时重新划分模块。

---

## 2. 文件与目录组织

推荐的通用顶层布局：

```text
<module>/          源码与头文件按模块组织
tests/<module>/    单元、集成与 live 测试；文件名 Test_<行为>.cc
examples/<name>/   每个示例独立目录，附 README
benchmarks/        仅在需要基准或性能测试时建立
docs/              architecture/、decisions/、guides/
scripts/           构建、CI 与维护脚本
cmake/             CMake 模块
.github/           workflows、PR 模板
```

- 根目录保留仓库入口文件（`AGENTS.md`、`README.md`、`CMakeLists.txt`、`.clang-format`、`.editorconfig`、`.gitignore`）；不另建工具工作流或任务状态目录。
- 每个公开类都应有可定位的公开头文件目标；职责内聚的小类型可以与相关公开类型同头声明，有非内联实现时配对 `.cc`。不因类的数量机械新增文件或目录层级。接口抽象放 `interface/` 子目录，纯虚基类使用 `I` 前缀；头文件用 `#pragma once`，目录层级与命名空间保持一致。
- include 顺序遵循仓库现有约定：对应头文件、标准库、项目公共头、子模块头；避免无关 include。

## 3. 语言、架构与依赖

- 新增代码以 C++17 为基线，不得静默提升标准；遵循目标仓库的 CMake 配置。
- 核心接口不依赖具体扩展或业务实现；传输与外部 adapter 由专属层负责，应用层负责业务接口；不预建万能协议或生成器平台。调用方只链接所需模块，并固定已验收的跨仓版本。
- 复用评估顺序：标准库、已选定的第三方基础库、仓内能力、确有必要的新依赖。标准库已有成熟能力时不重复造轮子；保留自研实现须记录可复核的语义、性能、平台或生命周期差异。新依赖须先评估活跃度、架构/平台、许可、安全、体积与退出路径。
- 命名空间最多三层。公共头不暴露内部类型，也不让第三方类型、异常或线程模型渗入公共 API；无法隔离时说明兼容影响并独立审查。
- 模板用于类型安全和复用，避免技巧性或难诊断的元编程。adapter 优先采用 RAII、值语义/智能指针与 `std::chrono`，并明确类型安全错误和取消/生命周期。纯算法、类型工具、无状态小组件优先 header-only；有稳定 ABI、重状态、I/O 或明显编译成本时，可保留编译单元并说明理由。
- adapter 负责 I/O、错误映射、取消/关闭及资源生命周期；底层等待结束、逻辑关闭与物理回收不可混为一谈。依赖反转/回调不改变源码依赖方向。

---

## 4. API、错误与所有权

- 错误优先使用类型安全的状态/错误表达；保留现有模块内的返回码语义，不跨模块强行改写已公开契约。
- 不抛异常的接口声明 `noexcept`。状态用枚举显式表达，不依赖裸 `int` 常量。`volatile` 不能提供线程间同步；跨线程状态应按语义使用 `atomic` 或锁。需要多字段一致快照时，逐字段使用 `atomic` 不能保证快照一致性，应采用能维护整体不变量的同步方式。
- 工厂 `Create()` 可返回项目约定的指针类型；按需用 `PrivateTag` 或 `protected` 构造限制直接构造。`SPtr` 对应 `std::shared_ptr`，`UPtr` 对应 `std::unique_ptr`；裸指针仅用于明确的非拥有关系或受控场景。
- 明确每个对象、回调与异步事件的所有权和寿命；事件/回调跨越异步边界时，确需共享寿命则使用 `shared_ptr`。不为微观性能机械替换智能指针，所有权理由优先于指针形式。

## 5. 注释

注释说明 WHY，不复述代码已经表达的 WHAT。

**语言选择**

- 注释以中文为主；英文术语、标识符、API 名、错误原文保留原样。
- `assert`、控制台错误消息、异常文本使用英文，避免编码问题；业务 payload 不翻译。

**Doxygen 格式**

公开头文件使用 `/** @brief ... */` 或 `///` 说明职责与公开契约；`///<` 用于字段行尾注释。普通实现里的 WHY 行注释不机械加空 Doxygen 标签。不编造线程安全、错误或寿命承诺；不对每个局部变量加注释。

```cpp
// 好：说明设计意图与不变量
/**
 * @brief 管理连接的借用与归还。
 *
 * 归还时不得持有业务锁；析构通知不抛异常、不挂起。
 */
class ConnectionPool { ... };

// 好：WHY 行注释
// 此处先关闭写端，确保读端收到 EOF 后再回收缓冲区
close(write_fd_);

// 不好：复述 WHAT
// 调用 close 关闭 write_fd_
close(write_fd_);
```

**时序与所有权约束**

涉及线程/协程交错、挂起/唤醒、取消、事件顺序、所有权或资源关闭时，写明必须成立的约束；复杂机制用多行注释说明设计意图与事件流。复杂关系确有收益时才用小图，不强制每处加图。

**历史与过程信息**

不在注释或长期文档里留 Issue/PR 号、审查/阶段代号、契约行号或临时版本标记；过程关联放在 commit、PR 或 Issue 中。允许保留协议/RFC 编号和指向稳定 ADR 文件的引用。

```cpp
// 不好：堆砌历史
// 2024-Q3 审查建议：原方案改为现方案，见 PR #42，修复了 #38

// 好：只保留当前状态的 WHY
// 使用单独的关闭通道而非共用信号量，以避免竞态唤醒
```

## 6. 技术设计取舍

**边界与职责**

从真实调用链与所有权判断模块边界，不从概念对称性推断。外部 API 与内部实现一起简化；合并仅转发或仅持有同一状态的层，删除不必要的 impl 暴露。对象粒度以职责内聚为准，不机械追求一类一文件或越多层越好，也不添加无消费者的抽象。

给出最小有效删改时，提供前后接口或调用路径对照；不以减少代码为由删除契约，不做泛化全库重构。

**必须保留的安全保证**

以下不得为减少代码量而删除：

- 截止期（deadline）与超时传播
- 背压（backpressure）与队列容量约束
- 错误可见性——错误须能被调用方观察到，不得静默吞掉
- 逻辑关闭（Close）与实际析构/物理回收的区别
- 资源归还责任——借用的资源须有明确归还路径
- `OutcomeUnknown` 类语义——操作结果不确定时须显式表达

**可观测性**

可观测组件不应意外持有业务对象的寿命；统计/追踪对象通过回调或弱引用与被观测对象解耦，以避免延迟析构。并发统计需要一致快照时，单字段 `atomic` 不足以保证多字段更新的原子性，须用适当同步保证快照不变量。

**适用条件**

规则须附适用条件约束，不要求所有模块套用同一机制。例如：

- RPC 的截止期传播机制适用于跨进程调用边界，不强制用于同进程内的轻量队列。
- queue 可使用标准容器或现有能力的薄封装，不需要独立的 Manager/Factory 链。

## 7. 测试

- 统一使用仓库已选定的测试框架；每个测试源文件构建为独立可执行目标。
- 测试文件命名为 `tests/<module>/Test_<行为>.cc`；CTest 名称统一为 `<module>.<行为>`。
- 每个测试按实际性质打 label：`smoke`（快速可用性）、`unit`（模块内边界）、`integration`（多模块协作，不依赖线上服务）、`live`（需要外部服务）、`perf`（基准/性能回归）。
- 新测试须在对应 `CMakeLists.txt` 注册到 CTest；核对构建开关、注册集合及 CI 执行路径。
- 并发/生命周期用例先证明已进入目标阶段，再注入故障或关闭，检查结果和资源收口；用同步原语建立时序，固定 `sleep` 或通过数量不能替代阶段证据。
- 测试 hook 须走正式可复用路径，正常使用者也可使用；不把匿名全局测试门直接变成生产全局 API。需要公共配置时用有限实例级能力，写清回调域、是否可挂起、寿命与清理；真实集成测试须保留，fake 不替代真实验收。
- 权限、环境或依赖不足时明确标为 `BLOCKED`，不以 stub、跳过断言或放宽检查伪装完成。

---

## 8. 示例

- 每个示例放在 `examples/<name>/`，附 `README.md`，说明演示内容、运行方式和期望输出。
- 示例只展示用法；断言和验收逻辑写进 `tests/`，不在示例中用断言充当测试。
- CI 编译全部示例；依赖外部服务的示例只编译、不在普通 CI 中运行。

## 9. 文档分类与维护

| 位置 | 内容与维护规则 |
|---|---|
| `README.md` | 项目是什么、当前状态、最短构建/使用路径、文档地图；不超过 200 行，不放 API 全表或流程正文。 |
| `docs/architecture/` | 稳定架构设计与契约；记录目标契约，变更随 PR 审查。 |
| `docs/decisions/NNNN-<slug>.md` | ADR；编号唯一且递增。合入后不改正文，只追加「已被 NNNN 取代」。 |
| `docs/guides/` | 操作指南；一个主题一篇，随代码在同一 PR 更新。 |
| 仓库外 / PR / Issue / CI artifact | 运行证据、审查报告、阶段计划和会话记录；不作为长期文档提交。 |

- 一事一处：一个事实只在一篇文档写全，其他文档链接到它。README 只做入口，不复制 API 或流程正文。
- 标题和文件名写主题，不写 Issue/PR 号、阶段代号或日期；ADR 编号是唯一的编号例外。
- 文档与对应代码在同一 PR 更新；被取代的文档直接删除，历史交给 Git。文档改动运行 `git diff --check` 并核对引用路径和命令。
- 长期资产按未来维护/决策需要判断；运行证据、原始日志、构建产物、凭据和私有路径不入仓。

## 10. 格式、构建与警告

- C++ 格式参数由 `.clang-format` 定义；`.editorconfig` 统一 UTF-8、LF、缩进和文件末尾换行。
- CI 只对 PR 改动行运行 `clang-format-diff`；不强制格式化存量代码。全仓格式化须单独决策和提交，不夹带在功能变更中。
- 不得引入新编译器警告；新模块/测试须接入相应 `CMakeLists.txt`。
- CI workflow 只编排，执行逻辑放 `scripts/ci/`；CI 变更及系统级安装均需事先确认。

## 11. Review 要点

**优先级**

缺陷与安全风险优先，流程合规性其次。少流程，验证力度随风险；用户未要求的不顺手扩张。

**共性检查项**

- 注释是否自然、是否反映当前状态：去历史堆砌，决策放 docs/ADR，保留必要的 WHY 与竞争/所有权不变量。
- 抽象是否过碎：合并仅转发或仅持有同一状态的层；对象设计以职责内聚为准。
- 共享状态一致性：并发写多字段时须保证快照不变量，不以单字段 atomic 误称一致快照。
- 失败/关闭/并发路径：错误是否可见、Close 与析构是否区分、资源归还路径是否明确。
- 测试区分力：测试须能区分正确与错误实现；fixture 只补时序控制，不能替代真实后端集成。

**验收与完成标准**

完成/通过须有绑定准确版本的实测证据；未跑、跳过、失败须分开说明，不以 CI 全绿代替新路径验收。fake 不替代真实 TCP/外部服务集成证据。

**注释审查专项**

检查注释风格：去僵硬术语堆叠，复杂机制可用简短字符画辅助理解；对照好坏示例（见 §5）判断是否自然。不为注释搭建单独网站或新 CI。
