# 共用原则

适用所有设计、编码、评审和用例设计。这里只定义判断依据；具体职责从 [阅读入口](../README.md) 按场景展开，已读且未变的内容不重复加载。

## P1 责任先闭合

生命期、所有权和责任第一优先：谁创建与结束、谁持有或借用、谁承担失败和副作用，必须在成功、异常、取消、关闭各条路径上有归属。责任不只包括内存，还包括任务、回调、资源和业务结果。

## P2 封装应降低理解成本

在安全和责任闭合的前提下，简单、易用、可靠优先于更多特性和性能。内部可以复杂，对外概念和操作应少。常规使用与排障应能依靠公开契约和诊断入口，不必先学内部状态机；深度根因分析仍可下钻。

## P3 代价与后果不能隐瞒

没有无代价的决策。使用者应事先知道能力边界，发生问题时知道结果和影响。内部恢复且外部语义未受影响，不必逐个上报内部异常；不能借恢复或封装掩盖重复执行、数据变化、延迟、费用等副作用，也不能把未知结果报成功。

## P4 扩展能力不能夺走控制权

灵活且可控的 hook 有价值；必须严格控制的路径禁止不可控外部逻辑。只读通常风险较低，但仍可能阻塞、抛异常、重入或泄露信息。扩展机制须交代原理、权限边界、寿命和风险，不能只靠名称或使用约定声称安全。

## P5 可观测性必须可用

设计时就提供状态、失败原因和排查入口。profiler、debug、trace 等细粒度能力可以选配或默认关闭，但应有实际可用的接入方式；选择与系统规模匹配的能力，不为每个值类型造监控模块。观测自身的开销和局限也要说明。

## P6 用工程化消除稳定的重复

反复产出大量类同代码，先检查是否缺少可复用能力、合适的数据表达或自动化，不永久逐处复制修补。先确认共同语义，再复用或重构；不因外形相似就搭通用框架。新增抽象、依赖或工具应降低整体理解与维护成本。
