# 长程任务的多智能体工作流

**何时读**：一项长程任务（跨多个阶段、耗时长或会跨会话）要拆给多个智能体并行或接力完成时。本文用图说明什么是好的工作流、什么是坏的，不绑定具体调度器（DAG、看板、脚本均可）、模型或命令，也不授予提交、推送、合并、改 CI 的权限。

工作包：一个执行者能独立交付、独立验收的一块工作，调度器里叫节点、卡片还是任务都一样。

## 1. 好的工作流

```text
开工核对（依赖 / 分支 / 是否 latest）
   │
冻结目标与验收
   │
调研+设计（读现有代码、定新形态，合为一个包）
   │  产物：目标类图 + 设计范围（改什么、不改什么）
   │
   ├─ 编码包 1：模块 A（含编译） ─┐
   ├─ 编码包 2：模块 B（含编译） ─┼─ 并行：写入隔离，耦合只在冻结接口（仅低耦合或用户要求时）
   └─ 测试用例设计（只依据契约） ─┘
   │
收尾测试（按影响范围，复用缓存）
   │  └─ 失败 ─> 带复现命令回到对应编码包修复 ─> 回到收尾测试（先复测失败项，再扩大）
   │ 通过
   │
独立审查
   │
验收（回读产物与证据）
```

好在哪：

- **起点对**：先核对依赖和分支基线，后面的结论才有依据。
- **读代码和写设计合成一个包**：调研得到的理解直接变成设计，产物是目标类图和设计范围；编码包拿着明确的目标直接写，不重读全部旧代码，也不再另做设计。目标一眼清楚的小改动不需要类图，设计与编码放在同一个包里。
- **编码连续完成**：中途只编译，不跑测试。
- **默认不并行**：整个需求在同一个 worktree 里按顺序做；只有用户明确要求，或项目规模大、模块耦合低时才并行，此时包 1、包 2 写入互不相交，耦合只在已冻结的接口上，各用独立的 worktree 和构建目录（见 2.4）。
- **测试在编码结束后集中做**：范围按影响范围选，不默认全量；已通过且输入没变的结果复用。用例依据契约设计，所以不会照着实现写断言。
- **失败回到编码修复**：测试失败时带复现命令交回编码，修好后先复测失败项，再按范围扩大。测试与编码由不同执行者承担。
- **验收看产物**：规划者回读产物与证据，不凭子代理自述；审查者是没参与编写的人。

## 2. 坏的工作流

### 2.1 按动作切分

```text
读代码(代理 1) ──> 写设计(代理 2) ──> 写代码(代理 3) ──> 编译(代理 4) ──> 测试(代理 5)

※ 每个 ──> 都是一次交接，上下文逐次丢失
```

坏在：每一次交接都丢上下文，交接文件比实际工作还长；读代码的理解没有直接变成设计，设计又没有落成可评审的产物。
改为：读代码和写设计合成一个「调研+设计」包，产物是目标类图和设计范围；编码包拿着它直接写，编译后进入测试和评审。例如某模块重写：

```text
调研+设计（读现有代码，定新模块形态）──> 编码（含编译）──> 测试 ──> 评审
         产物：目标类图 + 设计范围
```

好处：读代码得到的理解直接成为设计依据，少两次交接；类图是可评审的产物，方向错了在这里就能发现，不用等到代码写完。切点应落在能被评审的产物上，而不是落在读、写、编译这些动作上。

### 2.2 边写边测，最后全量

```text
写一个函数 ──> 跑测试 ──> 再写一个 ──> 跑测试 ──> …… ──> 收尾再跑全量回归

※ 前半段：测试散在编码里，反复打断
※ 后半段：没受影响的部分又重跑一遍
```

坏在：测试散在编码过程里，每次都打断思路，累计耗时最长；收尾全量又把没受影响的部分重跑一遍。
改为：编码连续完成，编码结束后测一次，范围按影响范围选，缓存能命中的不重跑。

### 2.3 自己写、自己测、改断言变绿

```text
代理写实现 ──> 同一代理写断言 ──> 跑测试
                                    │
                                  失败 ──> 改断言 / 删用例 ──> 全绿，宣布完成
```

坏在：断言迁就实现，绿灯不能证明契约成立；「改断言让它变绿」把缺陷藏了起来。
改为：用例依据契约，由另一个执行者写。失败先分清层次：产品缺陷交回编码修复，测试自身缺陷由测试方修，环境或依赖问题报告给规划者，不由任何一方改对方的产物。

### 2.4 并行：不隔离，或耦合太重

```text
冻结目标
   │
   ├─ 包 1 ─┐
   └─ 包 2 ─┴─> 同时改 CMakeLists.txt，共用 build/    ← 冲突点
```

坏在：源文件不同，但共享文件、构建目录、端口、测试数据、Git 索引照样冲突；worktree 只隔离文件和索引。

还有一种更常见的坏：为并行而并行，把耦合很重的需求拆到多个 worktree。

```text
需求（一个库，模块之间耦合重）
   │
   ├─ worktree A：改模块 1 ─┐
   └─ worktree B：改模块 2 ─┴─> 合并时在共享接口上冲突，要人工协调
                                 另外各多一份依赖、构建目录和缓存竞争
```

改为：**默认整个需求在同一个 worktree 里完成**，包按顺序做。只有两种情况才开多个 worktree：

- 用户明确下发「在两个 worktree 上工作」；
- 项目规模大，且模块或服务之间耦合低。

原因：

- worktree 只隔离文件和索引，隔离不了接口、设计、构建目录、依赖、端口和测试数据。耦合重时，冲突只是从编码阶段推到合并阶段，协调成本通常超过并行省下的时间。
- 每多一个 worktree，就多一份磁盘、依赖、构建目录和缓存竞争，也多一份清理成本。
- 判断看项目规模和耦合度。例如当前这样规模小、模块耦合重的库，整个需求放在同一个 worktree。以后若搭建有几十个模块的真实项目，模块或服务之间耦合低，就可以按模块或服务并行开 worktree。

确实并行时：共享文件指定唯一属主，其他包在交接里提需求；各 worktree 用独立的构建目录和依赖目录。

### 2.5 凭自述推进

```text
父会话被压缩或重开
   │
凭摘要判断「子代理应该跑完了」
   │
进入下一阶段，或重复派发在途工作    ← 漏做、重复做、把没跑的当成跑完了
```

坏在：对话摘要和子代理自述不是状态真源，会重复做、漏做，或把没跑的当成跑完了。
改为：落盘的运行记录和交接文件才是真源；恢复时先读记录、对账出已返回、在途、未派发的，再继续。长命令在包内跑完，或交给受管等待，不假定子代理退出后后台进程还在。

### 2.6 起点没核对

```text
凭印象开工（依赖没变，分支是最新）
   │
开发与测试
   │
合入前才发现基于旧基线 ──> 结论作废，整段返工
```

坏在：整段工作建立在没核对的前提上，返工成本在最后才暴露。
改为：开工前、测试前各核对一次依赖库、分支和是否基于 latest，见根 `README.md`「开工与测试前的核对」。

## 3. 工作包多大合适

| | 信号 | 处理 |
|---|---|---|
| 太大 | 验收要分好几条才说得清；中途必然被压缩；失败后不知道从哪重来 | 先按阶段（契约冻结、实现完成、测试通过、审查通过）切，再按模块切，高风险路径（等待、唤醒、取消竞争、对象寿命）单独成包，便于单独审查 |
| 合适 | 验收一句话说清；交接一页写完；与其他包的耦合只在冻结接口；一次上下文内能连续做完 | 保持 |
| 太小 | 交接和核对的成本超过工作量；两个包总改同一批文件；一个包的验收要等另一个包的实现细节 | 合并 |

实际经过里的正反例：

正例

- **连贯工作合成一包**（2026-11-13，coroutine 接入公共规范 submodule）：加 submodule、改 5 处入口文档、保留本仓规则、不启用未提交的 hooks，由同一个执行者在同一个 worktree 连续做完。验收一句话说得清：入口链接都存在、submodule 固定在已提交版本、`git diff --check` 通过。之后一次独立审查，结论 ship，无遗留问题。
- **高风险文件单独成包，修复留在包内**（同日，coroutine `AGENTS.md` 重写）：受保护文件独立成包并送独立审查；审查提出 5 条 P2（旧约束被删弱）后，在原包里按旧措辞补回，不新开包。修复没有新增判断，所以没有再派第二轮审查。
- **复审范围跟着修复点收窄**（2026-08-16，asset rename 提交审查）：首审覆盖整批 5 个文件；修完 3 处文档问题后，复审只核这 3 处，不重审整批。
- **代码和对应文档放进同一个包**（本仓约定同一 PR 更新）：两者验收同一件事，拆开后互相等对方。

反例

- **一次做太多**（2026-11-04，公开仓迁移）：不做一次性大拆分，改成小包逐步迁移；skill 重构同理，不直接重写全部 41 个 skill，先建独立的 workflow 层，再按家族分批。
- **包小到不如自己做**：自己两分钟前刚写的文件，派子代理去核对其中三行，交接成本超过工作量。
- **流程比事情重**（2026-11-02）：多轮子代理审查、补修、证据核对，让流程本身比要做的事还重；之后改为先出设计交用户 review，通过后直接实现，复杂调度只用于执行。
- **验收已定还拆一堆包**：用户把单次测试定为 1 分钟，却围绕它设计了三版测量方案和一批审查节点；定好的验收直接照做，不另设方案。

## 4. 边界

- 本文是软性规则，靠任务书和交接文件落实；宿主权限、钩子与沙箱才是硬约束。
- 授权不在本文范围：commit、push、开 PR、CI/发布变更、新依赖等仍按各仓规范先取得授权。
- 受保护文件、公共契约、等待/唤醒/取消竞争与对象寿命路径，仍须没参与编写的审查者独立审查。
