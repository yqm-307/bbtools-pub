# 设计职责

**何时读**：新增或调整 API、模块边界、生命周期、失败处理、容量策略、关闭语义或扩展机制时。进入本文件前已读 `docs/00-principles/README.md`；本文件不回链原则层，也不要求读者返回根路由。

设计的交付物不是类图数量或接口草稿，而是调用者能理解、实现者能闭合、评审者能验证的契约。一个设计说明至少要让读者知道默认动作、失败后的选择、责任归属和可观察事实。

## 1. 先确定责任，再确定接口

沿真实调用链标出创建者、owner、借用者、异步执行者和最终释放点。对成功、构造失败、部分安装、取消、重复关闭、连接断开和通知失败分别问一次“谁收口”。如果对象跨异步边界，必须写清谁保证它和被引用状态存活到哪个事件。

正例：`Submit()` 接受任务后返回一个有明确状态的句柄；句柄、队列和执行器分别说明谁持有任务数据、取消如何生效、队列拒绝时额度如何归还。

反例：`Start()` 返回成功，后台线程捕获了裸指针；文档只写“调用者不要太早销毁”，没有可验证的寿命协议。

设计检查：

- 是否存在多个“看起来都负责”的释放者？
- 失败路径是否会留下半安装回调、未归还容量或悬空借用？
- 关闭后新调用、在途调用和迟到通知分别是什么结果？
- 公共契约能否表达未知结果，而不是强行二选一成功/失败？

## 2. 从用户动作设计默认路径

先写调用者想完成的动作，再决定内部对象和层次。默认路径只要求必要输入和一个清晰结果；高级策略作为显式选项，不把内部状态机、回收链和配置矩阵变成必修课。

正例：调用者只需创建服务、提交请求、读取结果、调用 `Close()`；内部如何复用连接、安排协程、统计会话由实现封装。出现异常时，调用者能从返回结果或状态查询知道是否需要重试。

反例：为了执行一次普通请求，调用者必须先创建三个内部 manager、选择五个阶段开关，再手动关闭内部队列和连接。

保留层次的标准不是“层越少越好”。合并没有独立语义的转发和重复状态；保留真正承担不同责任的边界，例如协议适配、资源生命周期和业务策略。只改名、把类搬进 `detail` 或减少公开方法数，都不能单独证明设计变简单。

## 3. 把兜底写成用户能处理的行为

### 时间边界

`deadline` 是“最晚等到什么时候”，`timeout` 是等待时长。两者都用于阻止异常无限等待，不用于让正常路径靠碰运气调度。必须说明超时是否停止底层工作、对端是否可能已经执行、迟到结果如何处理；不能确认时使用明确的未知状态。

正例：超过 deadline 后返回 `OutcomeUnknown`，同时提供查询或去重入口。

反例：发生 timeout 就返回“远端未执行”，但底层取消并不可靠。

### 容量与背压

写出容量边界以及等待、拒绝、限流、降级或丢弃策略。背压也是常态流控，不只是在灾难时才存在。说明谁承担重试、延迟、数据丢失、顺序变化和公平性后果，禁止无界排队。

正例：队列满时拒绝新任务并返回可区分的容量错误，调用者知道是否可稍后重试。

反例：内部队列无限增长，直到内存耗尽才让调用者看到失败。

### 内部恢复与外部信号

内部恢复且外部语义没有变化时，不必把实现细节逐个上报；但任何影响结果、延迟承诺、重复请求、数据、费用或资源的副作用都必须可感知。无法处理的错误至少要让调用者知道“发生了无法处理的问题”。通知失败也需要有可观测处理。

### Close 的服务语义

说明关闭了什么服务、关闭后哪些调用被拒绝、在途任务和回调如何处理、是否等待。自有资源回收复杂度由内部承担；不能静默关闭借用的共享资源。`Close()` 是服务语义，不等于销毁对象，也不能成为放弃回收责任的借口。

## 4. Hook 的控制契约

只在确有扩展或观测价值的地方提供 hook，优先使用受限事件和不可变快照。设计说明至少回答：

- 触发阶段、执行线程/协程、是否持锁、同步还是异步；
- 可读写的状态，是否允许挂起、重入和并发改配置；
- callback 及其引用对象的持有者、注销动作和在途调用边界；
- 阻塞、耗时、异常和敏感数据如何影响主流程；
- 哪些关键不变量保护区禁止外部逻辑进入。

正例：状态提交后创建不可变快照，回调只观察；注销返回前等待在途调用收口，或者明确注销后仍可能收到的事件。

反例：在持锁、析构、准入或额度分配路径调用任意用户函数，要求“请快速返回”并用 timeout 声称可以强行终止 C++ 回调。

## 5. 观测与取舍

列出状态、错误、统计和诊断入口；说明精度、一致性、开销、开关和敏感数据边界。跨多个锁取值时不能承诺同一时刻快照，除非实现真的提供对应同步。

比较方案时写收益、代价、能力上限和放弃的方案。不要用“类更少”“代码更短”代替复杂度判断；要看调用步骤、使用者需要理解的概念和常见故障的排查路径。

需要将复杂度判断变成指标、增量告警和有理由的例外时，读 [语义复杂度评估口径](semantic-complexity.md)。该专项定义完整目标口径；首版 CLI 的入口和实现边界见根路由中的本地工程工具，CI 尚未接入。

## 6. 语义变化要直接迁移当前契约

如果 badcase 证明当前接口、参数、状态或概念已经不准确，先修改设计中的当前定义，再同步代码、测试、文档和提示词。不要在旧接口说明后追加 issue 号、阶段编号或“后来特殊处理”的长补丁。

反例：`这个接口提供 a 功能，参数是 b、c；在 #213 中因为某个问题所以后来变成 d。` 调用者仍不知道现在应依赖 a 还是 d。

正例：`这个接口提供 d（新的概念）功能；参数是 b、c；结果、错误和关闭行为按 d 的契约处理。` 必要的历史兼容原因单独写在 ADR 或迁移说明中，并只保留当前决策需要的部分。

如果旧行为仍被外部消费者依赖，设计必须明确兼容窗口、迁移方式和停止时间；这属于当前契约的一部分。若旧行为已经不再属于支持范围，就删除旧定义，避免让两个概念并存。

**做到什么程度算够**：调用者能完成默认动作并处理结果；实现者知道每份责任、不变量和失败收口；评审者有可验证的契约；语义修正不会留下互相冲突的旧说明。

## 7. 框架只做目标承诺，不做完美承诺

框架层提供简单、透明、可靠的服务，不追求完美。好的框架是清晰、简约、可靠的，而不是面面俱到的。

- 只承诺目标场景需要的行为。排空、等待全部在途完成、跨任意故障的精确一次这类“完美承诺”，默认交给上层服务决定；确需提供时，必须先说明目标场景为什么需要，以及它增加了多少状态、分支和公开接口。
- 实现优雅优先于功能多。为实现某个功能而增加系统复杂度前，必须审慎评估：不加会让目标场景失败吗？能由上层用已有接口组合出来吗？
- 评审时把“这个承诺要多少额外机制来兑现”当作成本，与功能收益放在一起判断。

反例：为承诺“关闭时一定排空所有在途请求”，在 Server 里加入排空等待、超时、状态机和多个公开接口，而调用者只需要“停止接收，剩余由我自己处理”。
