# Review 职责

**何时读**：评审代码、设计、文档、测试或构建相关改动时。先读共用原则，再进入本文件；本文件给出所有 Review 的共同判断顺序，只有触发生命周期、并发、关闭、hook 或观测风险时才进入本目录的 [生命周期与扩展 Review](lifecycle.md)。

Review 的任务是用证据判断“这版是否正确、是否满足要求、风险是否可接受”，不是替作者补代码，也不是把所有偏好都升级成阻塞缺陷。审查通过不自动授予提交、推送、合并或权限修改。

## 1. 先固定审查对象

- 记录基线、候选 HEAD、分支和工作区范围；包含未跟踪的新文件，不能只看空的 tracked diff。
- 把用户要求拆成可判断的规格项，分别判断“有没有缺陷”和“是否做到了要求”。
- 作者自述、工具外层退出码、空过滤、旧版本结果和“应该安全”都不是充分证据。

正例：先绑定 11 个候选文件及其 SHA，再逐项审查；发现一个命令实际没有构建目标，就把它标为验证缺口。

反例：只读当前 HEAD 的 committed diff，漏掉未跟踪公共头；看到历史 39/39 通过就直接说当前新增路径通过。

## 2. 按优先级审查

### 责任和失败路径

沿 P1 检查创建、持有、借用、异步存活、取消、关闭、析构、回调和资源归还。优先关注可能造成悬空访问、额度泄漏、结果误报或副作用隐藏的路径。

### 上层理解成本

沿 P2 看默认调用路径、概念数量、错误入口和常见排障。只改名、搬入 `detail`、减少公开成员数或增加一层适配器，不能单独证明封装变好。

### 代价、扩展和观测

沿 P3–P5 核对 timeout/deadline、满载策略、未知结果、hook 控制、回调注销、观测精度、保活影响和敏感数据。承诺要能回到实现或实际检查。

### 工程化与测试区分力

重复实现是否有共同责任？抽象是否降低总理解成本？测试是否能让正确和具体错误实现得出不同结果？覆盖率、通过数量、mock 调用次数都不能单独证明保护能力。

## 3. 检查 badcase 修正是否更新了当前契约

任何修改都要问：它是在修当前事实，还是把旧补丁继续贴在新行为后面？检查范围包括代码、公开接口、错误信息、注释、README、测试名称和断言、规则文件以及提示词。

必须发现的情况：

- 新概念已经改变，但旧定义还留在正文、示例或错误文本里；
- 文档写“在 #213 中因为……所以现在……”，却没有直接说明现在提供什么能力和参数语义；
- 代码行为已修正，提示词或 Review 检查项仍要求旧处理方式；
- 为了保留历史过程，在当前入口堆叠多个互相冲突的版本描述；
- badcase 已成为后来维护者必须知道的兼容、安全或迁移约束，却只留在不可见的讨论记录里。

正例：接口从 `a` 概念改成 `d`，Review 要求确认公共签名、实现、测试、文档和提示词都描述 `d`；历史 issue 只作为可追溯来源，不进入当前说明。

反例：公共文档写“这个接口提供 a；在 #213 后其实是 d”，测试仍按 a 断言，提示词也仍把返回值当 a。这样的修改即使代码能编译，也应指出契约迁移未完成。

历史只在它影响当前兼容性、迁移、安全或不可逆决策时保留，并且压缩成当前读者需要的最小背景。否则把它留在 commit、ADR、审查报告或私有证据中。

## 4. 按风险展开

| 改动或疑点 | 只展开什么 |
|---|---|
| 所有权、异步、并发、关闭、hook、资源回收 | [生命周期与扩展 Review](lifecycle.md) |
| API 或模块设计取舍 | 读取相关设计契约；不全量加载其他场景 |
| C++ 类型、公共头、构建兼容性 | 读取 C++ 规则的相关章节 |
| 文档、注释、示例或脱敏 | 读取文档与注释规则，核实事实和路径 |
| 新测试或覆盖有效性 | 读取用例设计；确有并发再进入并发专项 |

专项是增量检查，不是自动扩大范围。纯文档评审不会因为同仓有网络模块而进入生命周期专项。

## 4. 结论和证据

缺陷写清位置、触发条件、影响和证据；把建议、未覆盖风险和无法判断的问题分开。给出已检查且无问题的范围、未能判断的范围及原因；未跑、跳过、失败分别说明。

正例：`SessionHooks` 没有注销后在途调用协议，最小 ASan 复现 UAF，列为 P1；另一个“可以增加示例”的想法列为 P3 建议。

反例：因为没复现就写“没有问题”；因为 CI 外层返回 0 就写“全部通过”；因为风格不喜欢就用“可能不安全”阻塞，却没有触发路径。

必要复现用最小检查；不重跑作者整套测试，不为了没有新证据的猜测不断加审。独立性、候选绑定或验证条件不足时，明确报告，而不是补一段自我保证。

**做到什么程度算够**：候选和规格已绑定，主要责任与失败路径已检查，关键风险有真实证据，结论能区分缺陷/建议/缺口，且没有把未验证内容写成通过。
