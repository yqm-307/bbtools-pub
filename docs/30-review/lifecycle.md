# 生命周期与扩展 Review

**仅在这些风险存在时读**：拥有/借用关系、异步任务、共享状态、关闭、取消、hook、观测对象变化、容量归还或超时。先从 Review 入口进入；本文件是增量检查，不是所有评审的必读清单，也不要求回链上层。

## 1. 沿对象和责任追踪

找真实创建者、owner、借用者、最后释放点和观测者。逐项检查构造失败、部分安装、发布前取消、执行中关闭、重复关闭、最后一个业务引用释放以及回调在途时发生的销毁。

特别检查：

- 析构通知是否访问已经销毁的派生对象；
- 观测索引、统计对象或 debug handle 是否意外延长业务寿命；
- 借用的共享资源是否被某个 Close 静默关闭；
- 额度、队列项、连接和任务是否在成功、异常、取消和超时后归还；
- Close 的语义是否与实际析构/物理回收区分清楚。

正例：服务 Close 后停止接纳，已有任务按照契约结束或取消；内部回收连接，但不替调用者关闭仍被其他对象借用的共享资源。

反例：Close 只改状态位，后台任务继续访问外部对象；或者因为“资源封装在内部”就没有验证异常路径是否释放。

## 2. 沿共享状态和快照追踪

列出共享状态的每个读写者、线程/协程域和同步机制，判断同一不变量是否由同一套保护。逐字段 atomic、分次取锁或多个 getter 拼接，不能自动推出一致快照。

正例：统计快照在同一锁或版本协议下读取，文档承诺与实现一致；如果只能得到近似值，就明确采样时刻和一致性上限。

反例：文档写“所有字段来自同一时刻”，实现却先取 session，再取 queue，再取 connection；测试只断言最终数字看起来合理。

## 3. 沿 hook 的真实调用点追踪

对照设计层的控制契约检查真实执行位置、能修改的状态、并发配置、在途注销、重入和失败清理，而不只看公开说明。

至少问：

- 严格路径是否调用任意用户函数？
- 回调是否可能持锁、阻塞、挂起、抛异常或重入？
- 注册对象和被捕获引用由谁持有？注销返回后是否仍有在途调用？
- 出站/入站错误是否都释放握手记录、额度和连接？
- hook 是否能看到不应公开的 payload、凭据或内部地址？

正例：回调只接收不可变快照；注销协议明确等待或标注在途边界；异常被转换为可观察结果，主流程的责任记账仍能收口。

反例：只读参数被当成绝对安全；通过“请不要阻塞”的注释控制一个可以在持锁区域挂起的 callback；用全局开关隔离测试，却把它宣称成实例级正式扩展。

## 4. 沿时间、容量和关闭追踪

- 超时后检查底层工作是否仍可能继续、迟到结果如何处理、重试是否重复执行；不能假定 timeout 证明远端未执行。
- 容量达到边界时检查接纳、拒绝、等待、限流或降级策略，以及取消、异常和关闭后的额度归还。
- 关闭后检查新请求、在途请求、迟到回调和借用资源的可见结果；不能只检查 `Close()` 返回了成功。
- 通知失败时检查调用者是否仍能知道副作用，不能以内部日志替代外部信号。

## 5. 最小验证和交回

复用 `40-testcase` 中与本改动相关的事件序列；只做能证伪风险的最小复现，有限并发、硬超时、可清理。fake 可以控制交错，但不能代替需要真实网络或外部系统才能发现的证据。

正例：为注销时序建立“注册 → 进入回调 → 请求注销 → 回调继续/结束 → 对象销毁”的受控事件，并断言注销后的访问和资源责任。

反例：固定 sleep 后希望碰到竞态，或者看到一次没有崩溃就说生命周期安全。

**交回什么**：已证实的缺陷、触发条件、影响和证据；或明确尚未证明的风险和缺口。未复现不等于不存在，最后 diff 也不能证明中间编辑历史。
